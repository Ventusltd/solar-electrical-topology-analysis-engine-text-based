## 1. Purpose

The next development stint shall contain twenty small, ordered and reloadable steps.

The first ten steps close the inverter-block aggregate and establish a manifest-driven GitHub Actions worker.

The second ten steps deliver the first authoritative kernel-to-screen slice.

No step may absorb the next step merely because context remains available.

## 2. Governing cycle

Every step follows exactly:

```text
1. Build one contract.
2. Run one named test gate.
3. When and only when the gate passes, write the next active step.
```

A failed gate leaves the current step active.

The failure is repaired without opening the next step.

## 3. Memory and labour allocation

Quantum Spawn stores this sequence and its invariants.

A machine-readable manifest stores the active pointer, step states, test identifiers and evidence references.

Python scripts validate the manifest, select an allowlisted test and write canonical evidence.

GitHub Actions installs dependencies, runs the selected test, uploads evidence and performs the heavy validation work.

Code and tests remain implementation memory.

No long implementation diary shall be written for individual steps.

## 4. Safety rules

The workflow shall not execute arbitrary shell text read directly from the manifest.

The manifest shall contain allowlisted test identifiers.

A Python runner shall map each identifier to a repository-controlled command.

Automatic advancement shall require passing evidence whose step identifier, commit and manifest revision match the active state.

No workflow shall merge, overwrite production data or promote evidence automatically.

No browser calculation becomes engineering authority.

## 7. Manifest states

Only these states are permitted:

```text
planned
active
passed
blocked
```

Exactly one step is active.

All earlier steps are passed.

All later steps are planned.

A blocked step remains the active pointer until repaired.
