# 1. Purpose

This module defines the authoritative array engine. The array engine converts physical module placement into explicit electrical structure without introducing physics prematurely. It represents what is connected, in what order, through which terminals, into which MPPT inputs and ultimately into which inverter.

The first production target is one complete table containing 24 strings of 30 modules in series, giving 720 physical modules. This is a validated milestone, not a permanent hard limit. The same architecture must support other sensible string counts, module counts, MPPT counts and inverter-input arrangements without rewriting the engine.

# 2. Canonical Hierarchy

The authoritative hierarchy is:

```text
Module → String → Table → MPPT Input → MPPT → Inverter → Power Block → Plant
```

Every object has a stable identifier. Every parent-child relationship is explicit. No relationship may be inferred only from drawing position, naming convention or browser grouping.

A module belongs to one physical table and exactly one electrical string. A string contains an ordered sequence of module terminal connections. A string is assigned to one physical inverter input. That input belongs to one MPPT, and the MPPT belongs to one inverter.

# 3. Geometry and Topology Separation

Geometry answers where objects are located. Topology answers what is connected.

Moving an inverter changes home-run geometry but does not alter module membership. Reassigning a string to another input changes topology but need not move any module. Rotating a table changes coordinates but should preserve string membership unless the user explicitly regenerates stringing.

The kernel therefore maintains separate geometry, topology and route hashes. A change invalidates only the downstream receipts that depend upon it.

# 4. Module Objects

Every module instance references an equipment profile and contains a physical placement. Required instance fields include module identifier, table identifier, placement identifier, orientation, terminal locations, technology class and profile reference.

Future profile data may include dimensions, rated power, Isc, Voc, maximum series fuse rating, bifaciality, temperature coefficients and impulse-withstand evidence.

The placement engine owns coordinates. The topology engine owns terminal usage.

# 5. String Objects

A string is not merely a count of modules. It is an ordered electrical path.

Each string records a stable identifier, ordered module identifiers, explicit module-to-module terminal connections, positive and negative free terminals, wiring-strategy reference, table membership and inverter-input assignment state.

For the first fixture, every string contains exactly 30 modules. The engine validates that all 720 modules are used exactly once, no module appears in two strings, no required module is omitted, no string branches and every string has one positive and one negative free end.

Identical geometry and strategy inputs must always produce the same string membership and topology hash.

# 6. Sequential and Leapfrog Stringing

Sequential and leapfrog are topology and route-generation strategies over the same placed modules. They must not become separate calculation engines.

Sequential stringing links adjacent modules in physical progression and may require a long far-end return. Leapfrog alternates module connections to keep outgoing and returning paths closer together and usually reduce enclosed loop area.

Both strategies produce the same canonical connection schema. Downstream routing, physics and validation operate on explicit connections rather than strategy names.

The engine preserves total conductor length, positive length, negative length, route separation, crossings, parallel-run distance, maximum separation and enclosed loop area. A strategy is never judged only by total cable length.

# 7. MPPT and Input Modelling

An MPPT is not the same thing as a physical string input.

An inverter profile defines MPPT count, inputs per MPPT, current limits, voltage limits and permitted arrangements. The engine must not hard-code twelve or sixteen MPPTs, two strings per MPPT or 24 total strings.

A string assignment targets a physical input position. That input belongs to a named MPPT. Duplicate occupation is a hard failure. Unused inputs and MPPTs are valid but visible. Assignment limits come from the equipment profile rather than the browser.

# 8. Explicit Parallel Nodes

The engine distinguishes isolated inverter inputs from conductors physically paralleled before an input.

Required electrical node types include string terminal, connector, fuse, parallel junction, combiner bus, MPPT input, inverter DC bus and protective device.

Four strings through an explicit parallel junction are not equivalent to four separately isolated inputs merely sharing an MPPT label. This distinction is essential for reverse-current and overcurrent analysis.

# 9. Equipment Profiles

Equipment limits are data, not code.

Module and inverter profiles are versioned, source-referenced and replaceable. A profile may state maximum DC voltage, MPPT count, inputs per MPPT, current limits, backfeed evidence, power ratings and ambient derating curves.

Missing data remains missing and visible. The kernel never invents manufacturer values.

# 10. Validation Invariants

The array engine fails on duplicate identifiers, duplicate module use, omitted required modules, branched strings, open strings, invalid terminal direction, duplicate input occupation, assignments to nonexistent equipment, excess MPPT use and non-deterministic ordering.

Warnings may identify unused MPPTs, unusual string lengths, unequal strings on one MPPT, custom topologies or layouts differing from an approved configuration.

Validation does not redesign the array. It exposes facts and blocks authoritative receipts where invariants fail.

# 11. Whole-Table Receipt

The whole-table topology receipt includes module count, string count, ordered string membership, MPPT count, active input count, equipment-profile references, geometry hash, topology hash, assignment hash, warnings, errors and authority state.

The receipt forms the hand-off to conductor routing. Routing then produces explicit positive and negative paths to the movable inverter. Physics follows only after these paths exist.

# 12. Scaling Principle

A gigawatt plant must not require a new algorithm. It is built through deterministic replication of validated table and inverter-block objects. Each table remains independently inspectable and hashable. Aggregation occurs through explicit parent receipts rather than loss of detail.

# 13. Definition of Done

The initial array-engine milestone is complete when a caller can create one table of 24 strings with 30 modules in each, verify all 720 assignments, choose sequential or leapfrog stringing, assign every string to valid physical inverter inputs and receive a deterministic topology receipt.

The array engine establishes electrical structure. Geometry establishes physical reality. Routing joins the two. Only then may the project proceed to resistance, voltage drop, fault current, EMC, surge and standards validation.
