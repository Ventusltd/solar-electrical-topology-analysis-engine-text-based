# 1. Purpose

This module defines the authoritative array engine for the Solar Electrical Topology Analysis Engine. The array engine converts physical module placement into explicit electrical structure without introducing physics prematurely. Its responsibility is to represent what is connected, in what order, through which terminals, into which MPPT inputs, and ultimately into which inverter. It must remain deterministic, equipment-driven and independent from browser behaviour.

The first production target is one complete table containing twenty-four strings of thirty modules in series, giving seven hundred and twenty physical modules. This target is a validated milestone, not a permanent hard limit. The same architecture must support other sensible string counts, module counts, MPPT counts and inverter input arrangements without rewriting the engine.

# 2. Canonical Hierarchy

The authoritative hierarchy is:

Module → String → Table → MPPT Input → MPPT → Inverter → Power Block → Plant.

Every object must possess a stable identifier. Every parent-child relationship must be explicit. No relationship may be inferred only from drawing position, naming convention or browser grouping.

A module belongs to one physical table and may belong to exactly one electrical string. A string contains an ordered sequence of module terminal connections. A string is assigned to one physical inverter input. That input belongs to one MPPT. The MPPT belongs to one inverter. These relationships must remain independently inspectable and hashable.

# 3. Geometry and Topology Separation

Geometry answers where objects are located. Topology answers what is connected.

This separation is mandatory.

Moving an inverter changes the geometry of home-run conductors but does not alter module membership in a string. Reassigning a string from one MPPT input to another changes topology but need not move any module. Rotating a table changes module coordinates but should preserve string membership unless the user explicitly regenerates the stringing arrangement.

The kernel therefore maintains separate geometry, topology and route hashes. A change must invalidate only the downstream receipts that actually depend upon it.

# 4. Module Objects

Every module instance must reference an equipment profile and contain a physical placement. The instance must not copy electrical values unnecessarily; it should reference the canonical module profile by identifier and version.

Required instance fields include module identifier, table identifier, placement identifier, orientation, terminal locations, technology class and profile reference. Future profile data may include dimensions, rated power, Isc, Voc, maximum series fuse rating, bifaciality, temperature coefficients and impulse withstand evidence.

The module placement engine owns coordinates. The topology engine owns terminal usage.

# 5. String Objects

A string is not merely a count of modules. It is an ordered electrical path.

Each string must record:

- stable string identifier;
- ordered module identifiers;
- explicit module-to-module terminal connections;
- positive free terminal;
- negative free terminal;
- wiring strategy reference;
- table membership;
- inverter-input assignment state.

For the first acceptance fixture, every string contains exactly thirty modules. The engine must validate that all seven hundred and twenty modules are used exactly once, no module appears in two strings, no required module is omitted, no string branches, and every string has one positive and one negative free end.

The ordering must be deterministic. Identical geometry and identical strategy inputs must always produce the same string membership and topology hash.

# 6. Sequential and Leapfrog Stringing

Sequential and leapfrog are topology and route-generation strategies over the same placed modules. They must not become separate calculation engines.

Sequential stringing links adjacent modules in physical progression and may require a long far-end return conductor. Leapfrog stringing alternates module connections to keep outgoing and return paths closer together and usually reduce enclosed loop area.

Both strategies must produce the same canonical connection schema. The downstream routing, physics and validation layers therefore operate on explicit connections rather than strategy names.

The engine must preserve enough information to compare total conductor length, positive length, negative length, route separation, crossings, parallel-run distance, maximum separation and enclosed loop area. A strategy must never be judged only by total cable length.

# 7. MPPT and Input Modelling

An MPPT is not the same thing as a physical string input. This distinction must be explicit.

An inverter profile defines the number of MPPTs, the number of physical inputs associated with each MPPT, current limits, voltage limits and permitted input arrangements. The engine must not hard-code assumptions such as twelve MPPTs, sixteen MPPTs, two strings per MPPT or twenty-four total strings.

A string assignment therefore targets a physical input position. That input belongs to a named MPPT. Duplicate occupation of an input is a hard failure. Unused inputs and unused MPPTs are valid but visible. Assignment limits come from the equipment profile rather than the browser.

This architecture accommodates a twenty-four-string table connected to twelve active MPPTs, sixteen available MPPTs with some unused, or future inverter profiles supporting more inputs.

# 8. Explicit Parallel Nodes

The engine must distinguish isolated inverter inputs from conductors physically paralleled before an input.

Required electrical node types include string terminal, connector, fuse, parallel junction, combiner bus, MPPT input, inverter DC bus and protective device. Four strings connected through an explicit parallel junction are not equivalent to four separately isolated inputs merely sharing an MPPT label.

This distinction is essential for reverse-current and overcurrent analysis. Protection physics depends upon the actual fault-current neighbourhood, not a user-interface grouping.

# 9. Equipment Profiles

Equipment limits are data, not code.

Module and inverter profiles must be versioned, source-referenced and replaceable. The array engine validates structural compatibility using those profiles, while later physics calculates current, voltage and protection behaviour.

A profile may state maximum DC voltage, MPPT count, inputs per MPPT, input current limits, backfeed evidence, apparent-power ratings and ambient derating curves. Missing data must remain missing and visible. The kernel must never silently invent manufacturer values.

# 10. Validation Invariants

The array engine must fail on duplicate identifiers, duplicate module use, omitted required modules, branched strings, open strings, invalid terminal direction, duplicate inverter-input occupation, assignments to nonexistent equipment, excess MPPT use and non-deterministic ordering.

Warnings may identify unused MPPTs, unusual string lengths, unequal strings assigned to one MPPT, custom topologies, or layouts differing from an approved project configuration.

Validation does not redesign the array. It exposes facts and blocks authoritative receipts where invariants fail.

# 11. Whole-Table Receipt

The whole-table topology receipt must include module count, string count, ordered string membership, MPPT count, active input count, equipment-profile references, geometry hash, topology hash, assignment hash, warnings, errors and authority state.

The receipt forms the hand-off to conductor routing. Routing then produces explicit positive and negative paths to the movable inverter. Physics follows only after these paths exist.

# 12. Scaling Principle

A gigawatt plant must not require a new algorithm. It is built through deterministic replication of validated table and inverter-block objects. Each table remains independently inspectable and hashable. Aggregation occurs through explicit parent receipts rather than through loss of detail.

# 13. Definition of Done

The initial array-engine milestone is complete when a kernel caller can create one table of twenty-four strings with thirty modules in each string, verify all seven hundred and twenty module assignments, choose sequential or leapfrog stringing, assign every string to valid physical inverter inputs and receive a deterministic topology receipt.

The array engine establishes the electrical structure. Geometry establishes physical reality. Routing joins the two. Only then may the project proceed to resistance, voltage drop, fault current, EMC, surge and standards validation.
